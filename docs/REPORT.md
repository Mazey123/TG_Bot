# Отчёт по лабораторной работе

**Тема:** «Разработка интеллектуального бота с интеграцией внешних сервисов»
**Предметная область:** биржевой симулятор
**Стек:** Python 3.12, aiogram 3.3, SQLAlchemy 2 (async), SQLite, aiohttp.

---

## 1. Цель и задачи

**Цель:** разработать полнофункционального Telegram-бота — биржевой симулятор,
демонстрирующего асинхронное программирование, интеграцию внешних API,
проектирование базы данных и бизнес-логику средней сложности.

**Задачи:**

1. Спроектировать модульную архитектуру с разделением ответственности.
2. Реализовать асинхронную обработку событий и сетевых запросов.
3. Спроектировать БД для профилей, портфеля, сделок, достижений, квизов и кэша.
4. Интегрировать не менее двух внешних API с повторами и degradation.
5. Реализовать TTL-кэш и защиту от лишней нагрузки на API.
6. Построить FSM-сценарии торговли и квиза.
7. Добавить inline-клавиатуры, HTML-форматирование и медиа.
8. Реализовать XP, уровни, достижения, лидерборд и сброс прогресса.
9. Обеспечить валидацию, ORM-доступ и логирование без персональных данных.
10. Покрыть ключевую логику тестами.

---

## 2. Анализ предметной области

Пользователь получает виртуальный капитал (по умолчанию $10 000), покупает и
продаёт акции США и криптовалюты, наблюдает валютные пары. Стоимость портфеля
пересчитывается по текущим котировкам, а результат сделки сохраняется в истории.
Игровая мотивация строится на XP, уровнях, достижениях и таблице лидеров.
Дополнительно доступен квиз для проверки финансовой грамотности и ценовые алерты.

Ключевое ограничение: все операции виртуальные. Бот не работает с брокерским
счётом и не даёт инвестиционных рекомендаций.

---

## 3. Архитектура

Применяется слоистая архитектура, близкая к Clean Architecture / MVC:

| Слой | Каталог | Ответственность |
|---|---|---|
| Представление | `handlers/`, `keyboards/` | приём update, FSM, тексты, кнопки |
| Бизнес-логика | `services/` | сделки, оценка портфеля, квиз, кэш, API |
| Доступ к данным | `database/repo.py` | ORM-запросы, без commit в репозиториях |
| Модели | `database/models.py` | 8 таблиц |
| Инфраструктура | `middlewares/`, `utils/` | сессия, профиль, антифлуд, форматирование |
| Конфигурация | `config/settings.py` | `.env`, типы, секреты |

Поток обработки запроса:

```
Update → ThrottlingMiddleware → AppContextMiddleware
       → Router/Handler → Service → Repository → SQLAlchemy → SQLite
                              ↘ MarketService → aiohttp → внешние API
                                             ↘ CacheService → память/SQLite
```

Хендлеры не содержат SQL и не выполняют финансовые расчёты. Это упрощает
тестирование и исключает «спагетти-код».

## 4. Модель данных

| Таблица | Ключевые поля | Смысл |
|---|---|---|
| `users` | id, username, first_name, balance, xp, level, notifications_enabled, daily_streak, last_bonus_at | профиль и прогресс |
| `portfolio` | user_id, ticker, quantity, avg_buy_price; UNIQUE(user_id, ticker) | текущие позиции |
| `transactions` | side, quantity, price, total_amount, fee, realized_pnl, created_at | история сделок |
| `badges` | user_id, badge_code; UNIQUE | достижения |
| `quiz_attempts` | category, correct_answers, total_questions, score | история игр |
| `price_alerts` | ticker, direction, target_price, is_active, triggered_at | уведомления |
| `api_cache` | key, payload, expires_at, created_at | TTL-кэш API |
| `bot_meta` | key, value | служебные отметки |

Денежные значения хранятся в `Numeric(18,2)` и обрабатываются `Decimal`.
Количество — `Numeric(18,6)`. Это исключает ошибки округления `float`.

Покупка выполняется одной транзакцией: проверка и списание баланса через
условный `UPDATE users SET balance = balance - :cost WHERE balance >= :cost`,
затем upsert позиции и запись сделки. Продажа проверяет фактическое количество,
считает реализованный PnL `(price - avg) * qty - fee` и уменьшает/удаляет позицию.
Внутри процесса сделки пользователя сериализуются `asyncio.Lock`.

Для совместимости со старой версией БД при старте выполняется идемпотентная
миграция SQLite: добавляются новые колонки, переименовывается legacy-поле
`transactions.type` в `side`, создаются недостающие таблицы. Это позволяет
обновить существующую базу без потери профилей и портфеля.

## 5. Интеграция внешних сервисов

Использовано пять внешних HTTP-сервисов:

1. **Yahoo Finance Chart API** — котировки и история акций.
2. **Stooq CSV API** — резервные котировки акций.
3. **CoinGecko API** — криптовалюты и история.
4. **Frankfurter API** — курсы валют на основе данных ЕЦБ.
5. **QuickChart** — генерация PNG-графика для отправки фотографией.

Все запросы асинхронные (`aiohttp`), с таймаутом 6 секунд и двумя попытками.
При HTTP 429/5xx и сетевых ошибках используется экспоненциальная задержка.
После сбоя провайдер отключается на 90 секунд (circuit breaker), чтобы интерфейс
не ждал недоступную сеть.

Схема деградации:

```
память (TTL) → SQLite (TTL) → внешний API
                             ├─ retry
                             ├─ circuit breaker
                             └─ stale-кэш до 24 часов
                                  └─ демо-данные с явной пометкой
```

Пользователь всегда видит источник и предупреждение, если данные резервные.
Это принципиально: бот не выдаёт демо-цену за реальную.

Кэш: котировки — 60 секунд, валюты — 1 час, история — 30 минут. Хранение —
`MemoryTTLCache` плюс таблица `api_cache` (JSON, `expires_at`), что снижает
нагрузку на API и ускоряет повторные открытия карточек.

## 6. FSM-сценарии

### Торговля

```
waiting_ticker → waiting_quantity → confirming → результат
```

Пользователь выбирает инструмент кнопкой или вводит тикер, задаёт количество
(1/5/10, «всё» или вручную), видит цену, сумму, комиссию и новый баланс, затем
подтверждает. Ошибки валидации не меняют состояние БД. `/cancel` сбрасывает FSM.

### Квиз

```
категория → вопрос → проверка → следующий вопрос → результат
```

Вопросы выбираются случайно по 5 из 6 в каждой из трёх категорий. После ответа
показывается объяснение. Результат сохраняется в `quiz_attempts`, начисляются XP,
за 5/5 выдаётся достижение. Повторный callback на уже отвеченный вопрос
отклоняется по индексу — это защита от двойного нажатия.

## 7. Геймификация

* Уровень: `floor(sqrt(xp / 100)) + 1`.
* XP: 10–30 за сделку, +5 за прибыльную продажу, 20 за бонус, 15 за верный ответ
  в квизе, +25 за идеальный квиз.
* 7 достижений: первая сделка, первая прибыль, диверсификация, 10 сделок, «Кит»,
  идеальный квиз, серия бонусов.
* Ежедневный бонус: +$250, кулдаун 24 часа, серия — при входе не реже чем раз
  в 48 часов.
* Топ-10 по XP; для пользователя показывается его место.

## 8. UX и интерфейс

* Все основные действия — inline-кнопки; текстовый ввод только там, где нужен
  (тикер, количество, цена алерта).
* Единый стиль HTML-сообщений: жирный шрифт, `<code>`, эмодзи, progress bar.
* Карточка инструмента содержит цену, изменение, дневной диапазон, позицию и PnL.
* График за 30 дней отправляется как фотография; при ошибке — текстовая сводка.
* Главное меню, «Назад» и «В меню» есть на каждом экране.
* Сообщения короткие и адаптированы под мобильный Telegram.

## 9. Безопасность и надёжность

* Секреты — в `.env`; `pydantic-settings` + `SecretStr`; `.env` в `.gitignore`.
* Валидация: тикер `[A-Z0-9]{1,10}`, количество > 0 и ≤ 1 000 000, не более
  6 знаков после запятой, цена алерта > 0.
* ORM и параметризованные запросы; конкатенации SQL с вводом нет.
* HTML-экранирование имён и внешних строк.
* Антифлуд: 30 событий за 10 секунд на пользователя.
* Логи: псевдоним SHA-256 (`user_ref`) вместо Telegram ID/имени; фильтр вырезает
  токен и API-ключ.
* Глобальный error handler не раскрывает внутренние ошибки.
* Лимит активных алертов — 8 на пользователя.
* Поддержан `PROXY_URL` для HTTP/SOCKS5-прокси (Telegram Bot API и рыночные
  API). MTProto-прокси из Telegram-клиента для Bot API не подходит и отклоняется
  на этапе валидации.

## 10. Тестирование

Тесты запускаются стандартным `unittest`, не требуют токена, сети и pytest:

```powershell
.\venv\Scripts\python.exe -m unittest discover -s tests -v
```

Проверяется:

* парсинг Yahoo, Stooq, CoinGecko, Frankfurter;
* детерминированность демо-данных и построение URL графика;
* fallback на демо и stale-кэш при недоступности провайдеров;
* покупка, комиссия, средняя цена, продажа, PnL;
* откат при недостатке средств и запрет продажи больше позиции;
* запрет торговли валютными парами;
* TTL-кэш в памяти и SQLite;
* уровни, ежедневный бонус, банк вопросов, XP;
* валидация прокси (`socks5://`, `http://`; `mtproto://` отклоняется).

Результат прогона:

```
Ran 28 tests in 1.3s
OK
```

Дополнительно проверена сборка `Dispatcher` и полный сценарий обработки
`/start → /price → /buy → подтверждение → /portfolio → /quiz → callback'и`
через тестовую сессию Telegram API.

## 11. Заключение

В ходе работы разработан Telegram-бот «Биржевой симулятор», удовлетворяющий
требованиям SRS: модульная асинхронная архитектура, SQLite/ORM, FSM, интеграция
четырёх рыночных API и сервиса графиков, двухуровневый TTL-кэш, retry и
graceful degradation, inline-интерфейс, геймификация, лидерборд, настройки и
сброс прогресса, валидация и безопасное логирование.

Проект можно запустить локально одной командой после заполнения `.env`.
Для production-нагрузки архитектура допускает замену SQLite на PostgreSQL,
MemoryStorage на Redis и вынос фоновых алертов в отдельный worker.
